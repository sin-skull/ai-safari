# iPhone 17 Safari の確認手順

公開先: https://sin-skull.github.io/ai-safari/

## ホーム画面から開いたアプリの更新（0.12.7以降）

画面上部の「↻ アプリを更新」を押すと、オンラインで新しい版を確認し、必要なファイルの保存後に再読み込みする。同じ版でも再読み込みできる。モデル読み込みが止まっていても、このボタンは操作できる。実行中の処理は再読み込みで中断される。

会話履歴・記憶・保存モデルは削除しない。入力中の未送信文も同じウィンドウ内で復元する。オフラインでは接続が必要なことを表示し、再試行できる。

古い版にはこのボタンがない。最初の1回はオンラインでホーム画面アプリを完全に閉じて開き直し、更新取得を待ってからもう一度閉じて開く。画面下が0.12.7以降になったことを確認する。

更新試験: `node tests/pwa-update.cjs`。Windows WebKitとChromeで旧版から新版への切り替え、履歴・未送信文の保持、同じ版の再読み込み、オフライン時の再試行を確認。ChromeではOPFS内の保存ファイルが残ることも確認した。

## 最初の使い方

1. Wi-Fiに接続してSafariで公開先を開く。
2. 「スマホ用」のまま「会話を準備」を押す。初回はモデル約400MBと実行用ファイル約24MBを保存する。
3. 「会話できます」「画面と実行用ファイルを保存済み」の両方を確認する。
4. 短く「こんにちは。私の名前はサトルです」と送る。次に「私の名前は？」と聞く。
5. 機内モードにし、Wi-Fiもオフにして再読み込みする。履歴が戻ることを確認し、「会話を準備」→短い質問を送る。
6. 会話を数分続け、「止める」→次の質問、「メモリを解放」→再準備も試す。

ホーム画面への追加は任意。モデルは初回に取得する必要がある。Safariがサイトデータを消した場合は再取得が必要。

## うまくいかない場合

「動作記録を書き出す」で版・ブラウザ情報・段階・処理時間をJSONに保存できる。会話本文は含まない。落ちた後は同じページを開き直すと、前回途中だったことを表示する。自動的な再読み込み・モデルの再実行はしない。

- 準備の途中で再読み込みされた: 保存中か、モデル展開中かを記録する。
- 生成中に落ちた: 最初の文字が出たか、何回目の質問かを記録する。
- オフラインで開かない: オンラインで画面と実行用ファイルの保存完了を確認する。
- モデルが未保存: オンラインでそのモデルを一度準備する。スマホ用とPC用は同じ保存モデルを使う。最小モデルは別の保存データ。
- 日本語や内容がおかしい: 小型モデルの能力による可能性がある。技術的な動作成功と会話品質は分けて評価する。

## 検証記録（2026-10-13）

- 自動: 既存137件 + 会話制御・互換性10件、計147件成功。直列化、解放失敗時の二重割り当て防止、生成中の切り替え、停止、履歴と入力容量、オフライン用ファイルの完全性、ページ別キャッシュ、CPU互換版の選択を検証。
- Windows Chrome（初期候補LFM2・現在は最小モード）: 実モデルの取得・読み込み・日本語生成・続きの質問・履歴の再表示を確認。初回の短い生成は約19秒、続きの質問は約5秒（このPCでの参考値）。利用者の名前を自分の名前のように言うなど、日本語の品質には課題がある。
- Windows Chrome: OPFS/Workerを含むブラウザテスト138件が成功。390px幅のレイアウトを確認。配信サーバーを停止した状態でも画面を再読み込みし、保存済みLFM2モデルから生成できた（端末全体のネットワークを無効にした試験とは別）。
- Qwen3 CPU: モデル読み込み成功。長めの履歴を含む初回生成は最初の応答が出る前に約66秒で停止した。スマホでの待ち時間を実機確認する必要がある。停止はWorkerを終了する方式に改善し、再開時は準備ボタンで読み直す。
- Qwen3 GPU: 新規会話の短い回答は約1.1秒。ただし「猫の食 supply」のような英語混じりの不自然な日本語が出た。自然な会話品質を満たしたとは評価していない。
- Windows WebKit 26.5: 390×844、タッチイベント、CPU数4、crossOriginIsolated=falseで確認。表示・手動起動・配信元を切断した後の再読み込み・記憶画面/試験室への移動が成功。
- 同WebKit: 従来の自動判定では、実行時に `Memory64 is not enabled` で停止した。0.12.6ではCPUモードをWasm32互換版へ固定。配信元切断中に極小モデル（0.5MB）を1スレッドCPUで読み込み、8トークン生成に成功。これは約400MBの会話モデルのメモリ使用量・日本語品質を検証した結果ではない。
- Chromeの独立テスト環境: `context.setOffline(true)` で通信を無効にした後、同じ再読み込み・極小モデル生成・ページ遷移が成功。保存済み400MBモデルからの完全オフライン生成はこの自動試験の対象外。
- **iPhone 17 Safari: 未実施。iPhoneの動作保証・速度保証はしない。**
- 音声認識・音声会話: 未実装。まず上の文字会話の実機結果を確認してから進める。

## 開発用

`pnpm install --frozen-lockfile` → `pnpm test`。

Windowsでは `.mjs` のMIMEタイプが環境によって text/plain になるため、`python tests/serve.py` を使用する。`http://127.0.0.1:8766/tests/test.html` ではOPFS/Workerの実動作を含むテストを実行する。Service Workerを更新した直後は、次の再読み込みから新しい版になることがある。画面下の版番号を確認する。

最小のLFM2は生成できても日本語に誤りが多く、既定から外した。スマホ用/PC用の既定はQwen3 0.6B（Unsloth Q4_K_M）に変更。これは実機で落ちないことを保証する選定ではなく、会話品質とメモリ負荷を比較するための候補。

## PCでのSafari疑似検証

```sh
npm install --no-save --package-lock=false playwright
npx playwright install webkit
node tests/mobile-webkit.cjs
```

テストは独立したブラウザと一時的な配信元を作り、ユーザーのブラウザ履歴・保存モデルには触れない。第1引数にPNGの保存先を渡すと画面も保存できる。ChromeをインストールしたPCでは、環境変数 `BROWSER_ENGINE=chromium` を指定するとブラウザ全体のオフライン切り替えも検証する。

- プリセットはiPhone 13の390px幅。iPhone 17そのものを再現したものではない。タッチイベントは検証するが、Windows WebKitのmaxTouchPointsは0を返す。
- Windows WebKitにはOPFSがないため、同環境ではアプリのモデル保存を検証できない。極小モデルの実行試験は保存処理を使わずBlobで直接読み込む。ChromeでのOPFS検証と区別する。
- WebKitの `setOffline(true)` はService Worker応答まで失敗させる既知の問題があるため、WebKit試験では配信元への接続を切断する。`navigator.onLine` はtrueのまま。単なる表示の偽装ではなく、未保存URLへの実際の通信失敗も確認する。[Playwright issue #42775](https://github.com/microsoft/playwright/issues/42775)
- iOSのメモリ不足によるタブ終了、Apple GPU、発熱、実機速度は再現しない。これらはiPhone 17 Safariの実機確認が必要。[Playwrightの端末エミュレーション](https://playwright.dev/docs/emulation)
